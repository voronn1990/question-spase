# Принятые условия переноса, v4.0.0

Это условия владельца навыка, а не автоматически принятые требования будущего исследовательского проекта.

| Основание | Действующее правило |
|---|---|
| Исходный вход вопросами; более позднее OWNER-SCOPE-05 добавляет цель | Действуют два явных режима: GOAL_TO_PLAN строит пространство исследования после утверждения точного Вектора, BANK_TO_PLAN сохраняет переданный банк. Примеры навыка не считаются пользовательским вводом. Прежнее ограничение «только готовые вопросы» заменено для GOAL_TO_PLAN. |
| «Роли это субагенты», включая Вектор, Индульгенцию, Реверс и Синтез | Обязательны 18 раздельных ролей: десять предметных, шесть операторов, планировщик, независимый аудитор. Координатор дополнительно управляет ими. |
| «Не под Trade… унифицированный по методологии» | Предметные компетенции выбираются заново для каждого проекта. Фиксированные финансовые пороги, торговые школы и численность примера не становятся нормой навыка. |
| «Не переусложняй», замечания D01–D10/H01–H16 | Используются нативные агенты, обычные файлы и небольшой локальный помощник со строго объявленной YAML-зависимостью. Отдельная платформа, сервер или база данных не нужны. |
| Исходники в ZIP не нужны | Полные исходные вложения и рабочие архивы автора исключены. Исполнимая методология находится в инструкциях, а соответствие первоисточнику — в coverage-map.md. Скрипты проверки входят в навык, поскольку нужны при его применении. |
| Прямое уточнение владельца от 2026-10-21 | Каталог дополнительных 14 приёмов восстановлен по предоставленной таблице. Анализ, индукция, дедукция и синтез являются базовыми действиями, а не четырьмя пунктами этого списка. |

Версия принятого банка может быть вычислена из SHA-256 его фактических байтов. Человекочитаемая метка не обязательна. Это техническая идентификация, она не меняет содержание или полномочия.

Совместимость с v3: сохраняется имя навыка `question-space`. Новое прямое ТЗ OWNER-SCOPE-02 заменяет прежние нормативные Markdown-отчёты: канонический запуск расположен в `runs/<run_id>/`; банк, versioned результаты/гейты, этапы `plan/S-000.yaml` и selected аудит `audit/final/<result_id>.yaml` имеют YAML-контракт. Свидетельства находятся в `runs/<run_id>/evidence/`; исходные файлы сохраняют свой формат. Markdown результата допускается только как автоматически построенное представление YAML. `RESEARCH.md`, `implementation_plan/00_Старт_и_допуск.md` и `AUDIT.md` больше не являются обязательными каноническими результатами нового запуска. Перенос старого исследования выполняется отдельным снимком и таблицей соответствия путей/хэшей по протоколу хранения. Ни новые названия, ни номер версии не делают старые проверки актуальными без проверки применимости.

Уточнение владельца от 2026-10-22 относится к квалификации этой версии: 50 вопросов достаточно для полного крупного испытания. Уже принятое нейтральное исследование 113 вопросов сохраняется целиком и завершает этот объём; отдельный прогон торгового проекта снят. Это изменение объёма испытания не задаёт размер банка будущего проекта и не сокращает 18 ролей, глубину исследования, шесть фаз, критические рецензии или восемь областей аудита. Навык применяется к любой предметной задаче; компетенции и критерии G/R определяются её входом.

Две оси границ независимы: обязательность требования и статус утверждения контракта. Один объект может быть одновременно жёстким требованием и утверждённым контрактом. Рабочее предположение не является разрешением менять ни одно из них.

Внешнее согласование необходимо только при действительно недостающем решении владельца или полномочии на зависимое действие. Внутренний гейт не требует повторного согласия пользователя. Разрешение исследовать и подготовить план не разрешает его внедрение.

## Дополнительное ТЗ OWNER-SCOPE-02

Принято 2026-10-21, SHA-256 входа `6f4bfe1228a3fe6f3d064bc27c94b9be4a58608b5eb6e5d9f6e1ba179dc49426`. Оно имеет приоритет над прежними именами выходных Markdown-файлов. Markdown в SKILL.md и references — инструкции применения, а не дубли нормативных результатов исследования.

Сохранить раздельно неизменяемые исходные данные, принятое знание, оперативное состояние и замороженный нормативный результат. YAML имеет безопасный разбор, явные типы ID/версий/дат, контроль дубликатов/тегов/неявных преобразований; большие аргументы остаются многострочными значениями, а не обрезаются ради схемы.

Context7 предусмотрен как штатный MCP для каждой роли. Работоспособность подтверждается реальным дочерним вызовом с версией проекта и свидетельством MCP_DOCUMENTATION, а не конфигурацией или запросом Root. При недоступности фиксируется TOOL_UNAVAILABLE; независимая работа продолжается, затронутая проверка остаётся открытой. Ключи не входят в навык или результаты.

Готовность новой версии требует отдельно подтверждённых соответствия пакета, локальной устойчивости, реального малого запуска 18 ролей, Context7 в дочерних ролях и реального крупного исследования со сравнимыми измерениями v3. Синтетические 230/300 записей проверяют только структуру. Установка пакета не означает READY всей версии; недоступные измерения имеют NOT_RUN/UNAVAILABLE без выдуманных процентов.

## Дополнительное ТЗ OWNER-SCOPE-05

Вход `dc8a91316af55a47fff6323a2f9681bed2f0da20017429b780b3118df5002167` вводит четыре подготовительные стадии перед существующими шестью основными. Полный контракт подготовки находится в [preparation.md](../references/preparation.md); прежние запреты начинать с одной цели и генерировать вопросы без отдельного запроса заменены только для GOAL_TO_PLAN.

В GOAL_TO_PLAN координатор уточняет только решения, принадлежащие владельцу. Выбор алгоритма, архитектуры, механизма и проверка гипотез остаются исследованием. Требуется явное утверждение конкретных байтов Вектора; молчание не является утверждением. После него те же десять реальных P независимо создают по десять начальных вопросов, затем вместе с существующими операторами расширяют и нормализуют пространство. Дополнительная роль генератора не вводится. Начальные позиции сохраняются до знакомства с чужими решениями.

200–300 содержательных уникальных вопросов — целевой диапазон расширения, а не основание добавлять повторы. Меньший банк требует обоснования достаточности и карты пробелов; критические вопросы сверх 300 сохраняются с планом ресурсов. Семантическое объединение сохраняет все источники; разные условия применимости не скрываются объединением. Допуск явно закрывает десять исходных областей подготовки. После допуска исследование и планирование продолжаются без второго запроса и повторной генерации.

В `BANK_TO_PLAN/APPROVED_RUN_IMPORT` неизменные G/R/полномочия позволяют использовать прежнее утверждение. Вектор, утверждение и исходное сообщение утверждения импортируются побайтно с происхождением; текущий OP-VECTOR подтверждает их применимость без переутверждения. `BANK_TO_PLAN/EXTERNAL_READY_BANK` принимает exact согласованный внешний банк без выдуманных foreign approval artifacts, создаёт local Vector/applicability и получает только действительно необходимое approval/authority; второй банк не генерируется. Изменённые или недоказанные условия не получают допуск. Симулированное утверждение принадлежит только явно обозначенному тесту и никогда не выдаётся за волю реального владельца.

Общий снимок, неизменяемый допуск и текущая версия плана связаны точными хэшами. Принятая история сохраняется, но модель и выпуск используют явно выбранную актуальную проекцию этапов. Восстановление сохраняет допустимые последующие состояния и не возвращает текущую версию к моменту допуска. Машинная проверка структуры не доказывает истинность семантических решений координатора. Состав методологии остаётся прежним: 18 ролей, 14 дополнительных приёмов, шесть основных этапов, восемь областей финального аудита и S-000.

## Дополнительное ТЗ OWNER-SCOPE-06

Вход `INPUTS/github-mcp-scope06.txt` SHA-256 `87e48cfd3cc438e75e0f62726ebc8b679e4df1f8af63c7610206d0385755c3bf` разрешает read-only исследование внешних инженерных механизмов через уже доступный native GitHub connector. Это transport-neutral методологическое расширение: runtime динамически обнаруживает read capabilities, Root утверждает exact task allowlist; plugin/provider configuration и remote mutation не разрешены. Видимые mutation tools и low-risk permission не являются технической read-only ACL attestation.

Четыре класса полномочий обязательны: A approved G/R, B verified current project state, C external implementations, D official versioned documentation. B/C не создают R. До первого собственного FRAMING десяти P coordinator shortlist/preferred mechanism скрыт. После freeze поиск идёт по required capability через direct, functional, alternative и negative-experience routes с finite value-of-information stop.

C хранится existing `EVIDENCE` subkind `EXTERNAL_IMPLEMENTATION`, без нового result type/storage/runtime. Exact commit/code/tests/receipts/origin/license/limits связываются с Q/D; transfer требует отдельного target applicability E. Divergence, Reverse, Synthesis, Planner и independent FINAL-AUDITOR применяют единый [GitHub protocol](../references/github.md). Все 12 actual child/MCP scenarios остаются `NOT_RUN` до сохранённого независимого протокола. Состав 18 ролей, шесть Core-фаз, 14 приёмов, две входные моды, S-000 и восемь областей аудита не меняется.
