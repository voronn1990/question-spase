# Фаза 2. Доказательные ответы

Проведи исследование в допущенном бюджете Q и сохрани запись по всему принятому банку. Каждый original Q входит ровно в одну выбранную текущую запись versioned принятого `answers/source-outcomes/<result_id>.yaml` с `artifact_type: SOURCE_OUTCOMES`; successor artifact добавляет `supersedes`, а initial artifact его не выдумывает. Его records содержат `original_q_ids`, `source_disposition`, `disposition_target_ids`, `answer_status`, `knowledge_state` и `evidence_ids`. Selector `current_source_outcomes` и lineage следуют [контракту v4.1](../contracts-v4.1.md#неизменяемая-история-и-текущие-версии). Для исследованного Q используй `author_assignment_id` и `answer_result_id` с отдельным exact `ANSWER` или `PRIMARY` того же run/snapshot и заявленного primary assignment/role/agent. Disposition использует `KEPT|REFINED|MERGED|CLOSED_BY_EVIDENCE|NOT_APPLICABLE|SPLIT`; target IDs обязательны для merge/evidence closure/split. `answer_status=ANSWERED|OPEN|NOT_APPLICABLE` остаётся отдельным; disposition `NOT_APPLICABLE` требует одноимённый answer status. Derived child после SPLIT получает собственный Q-ID и `parent_source_ids`, не повторяя original ID как второй current source outcome; MERGED сохраняет trace всех исходников. Исходный текст сохраняется, даже если несколько Q используют общее E. Первичный ответ роли сохраняется до чужой критики.

На фактическом старте `reconcile-effect` принимает observed provider/recipient E с `question_starts` по точным Q и каноническому handle. ACK оставляет неизвестные старты удержанными. `question-observe` принимает последующую независимую сверку по тому же claim и Q. `question-close` принимает точный независимый REVIEW по принятому ответу и его контексту, наблюдению о глубине и правилам исходного регламента. Для worked OPEN укажи оставшийся шаг проверки.

Для нерасследованного Q зафиксируй `question-gaps` с REVIEW над EVIDENCE `question_gaps`. В approved route и в исходе укажи `question_gap: {proof_id, proof_sha256, reason}` из точного текущего журнала. Запись использует `answer_status: OPEN` и `knowledge_state: UNKNOWN`. Пропусти поля автора ответа и ответа. Для derived Q сохрани его source parent. Пробел остаётся адресным ограничением аудита, а не единицей завершённой работы.

## Карточка ответа

Для простого факта достаточно точного ответа, применимого основания и границы. Для содержательного проектного Q раскрой:

1. фактическое состояние, требования, входы, версии и уже выполненные проверки;
2. ограничение и причину: установленное/гипотеза, область и конкурирующие объяснения;
3. опорный подход и минимум два содержательно иных механизма, когда это предметно возможно;
4. конкретный алгоритм/математическое правило/конечную процедуру, параметры, выбор и ошибки;
5. входы/выходы/зависимости: производитель, контракт, смысл, единицы, время доступности, потребитель и состояние;
6. измеренную либо явно оценочную стоимость подготовки, исследования, реализации и эксплуатации;
7. способность, ценность, вклад в G и классы, исключённые представлением;
8. первичные E, выполненные проверки, область вывода и пробелы;
9. заранее различимые положительный, отрицательный и граничный исходы; чувствительность проверки;
10. проектное следствие: сохранить/исправить/упростить/переиспользовать/заменить/отклонить/проверить, новые зависимости и риски.

Фразы «добавить ML», «оптимизировать» и «проверить» без механизма, границ и выхода не принимаются. Неприменимость альтернатив или теста объясняется предметно.

## Проекция отказа в ответе

Для существенного `NOT_G` укажи условия и логику `И/ИЛИ/порядок`, переход и механизм, область/основания, альтернативные пути, действие, отрицательную проверку и положительный результат после вмешательства. Различай:

- необходимое условие `G ⇒ N` в указанной области;
- достаточное условие провала `F ⇒ NOT_G`, не подразумевающее `NOT_F ⇒ G`;
- фактор риска;
- причинную гипотезу.

Когда это влияет на действие, найди минимальную достаточную комбинацию отказа в рассматриваемой модели; полный перебор не нужен. Общую точку отказа резервов проверяй отдельно.

Для своевременности задай: ранний наблюдаемый признак → окно действия → действие → проверка сохранённого результата. Если признак возможен лишь постфактум, скажи это. Различай устранение причины, разрыв перехода, обход, обнаружение и восстановление.

## Проверки и связи

При доступном разрешённом тесте выполни минимально достаточный. Проверь чувствительность на подходящем неверном входе. Для `NOT_RUN` дай точную процедуру, входы и причину. Укажи, какие Q ответ закрывает при данном исходе, какие D меняет и какие неизвестные открывает.

Общие расчёты и E переиспользуй по адресу, но вывод по Q остаётся отдельным. `author_assignment_id` указывает единственное назначение primary author, а `answer_result_id` — принятый immutable result `artifact_type: PRIMARY` или адресный `ANSWER` того же назначения/роли/агента/snapshot; объявленного статуса или несуществующего hash недостаточно. Один P-result `PRIMARY` может адресно покрывать связанный пакет Q этой P, но не другую роль/assignment. Отказ одного семейства решений не исключает остальные.

Перед принятием результата сравни frozen `assignment.assigned_ids.questions` с адресными outcomes этого exact assignment. Для каждого Q верни принятую ссылку либо явный `OPEN/NOT_APPLICABLE` с основанием и next path; лишний Q не закрывает пропущенный. `DONE`, общий вывод пакета, обнаружение одного дефекта или количество файлов не меняют знаменатель. Координатор возвращает точный список missing/duplicate/foreign Q и принимает только полный адресный result либо явно ограниченный partial result, который не закрывает assignment.

## GATE-2

PASS, когда 100% original Q имеют ровно один текущий outcome с допустимыми disposition/status/knowledge, одним принятым author assignment и answer result, включая `OPEN`/`NOT_APPLICABLE`; merge/split не создаёт конкурирующие current records; для ключевых Q определены mechanisms, alternatives, cost и distinguishing test; E воспроизводимы; central UNKNOWN видимы. Сохрани outcome в `gates/GATE-2.yaml`. Количество records, текст или confidence не заменяют полноту.

## External implementation evidence

Для ключевого technical Q после blind freeze применяй [GitHub-протокол](../github.md): исследуй concrete mechanism/inputs/conditions/assumptions/tests/current limits и отдельно transferability. Существенный reference сохраняй existing `EVIDENCE` subkind `EXTERNAL_IMPLEMENTATION`; README, stars, наличие code или чужой CI не являются ответом сами по себе. `TESTED` требует named receipt, `TRANSFER_VALIDATED` — target applicability E. Shared immutable E можно связать с несколькими Q/D без повторной загрузки bytes и без потери отдельных outcomes.

## Double-Iceberg evidence

После blind freeze сопоставь Q/E с exact position seeds и material unknowns. GATE-2 закрывает только конкретные material `DERIVED_Q`/E obligations, которые действительно возникли: ноль новых `DERIVED_Q` допустим, если original Q и accepted E/R/G полностью покрывают bounded model и нет qualifying unknown; каждый присутствующий новый Q остаётся typed, material, finite, nonduplicate и addressed, а critical coverage не отменяется. Финальная карта на этом гейте не выдумывается. E меняет статус только exact H/member/edge, к которому применима; bounded confirmed cause кодируется `CAUSAL_INFLUENCE` с complete `causal_confirmation`, а не голосованием или корреляцией.
