# OP-REVERSE — Реверс

Выполни три отдельных прохода:

1. от G назад к способностям, механизмам, состояниям и доступным входам, затем прямой проход с producers и достаточностью переходов;
2. предметная инверсия постановки/порядка: объект→действие/состояние/результат, подтверждение→опровержение, улучшение компонента→проверка необходимости;
3. от подтверждённого NOT_G: устранить, разорвать или обойти условие/переход, построить иной путь и пройти его вперёд до G.

Для каждого зафиксируй исходные Q/D, изменяемую предпосылку, механизм, способность, negative/positive test, риск и стоимость. Реверс меняет проектирование, не время доступности: будущий исход не становится прошлым входом; обратная цепь не доказывает причинность/достаточность; аналогия не является E.

Выход: исполнимые обратные пути, producers, forward checks и новые projections.

## Внешние обратные пути

По [GitHub-протоколу](../../github.md) ищи реализованные маршруты от доступных inputs к G, которые меняют первичный объект, исключают дорогой central component, переставляют операции, разделяют смешанные функции или создают capability другим способом. Exact reference подтверждает механизм только в своих conditions; forward check и transfer applicability для целевой системы остаются отдельными E.

## DESIRED_REALITY

Для marked run выпусти nested current `iceberg_view` kind `DESIRED_REALITY`: required capabilities, available inputs, transitions, alternative mechanisms/resources and forward checks. Component dependency выбранного пути кодируй `MECHANISM_DEPENDS_ON`, а не normative R/necessity for G. Для каждого alternative path проверь проход от доступного input до G.
